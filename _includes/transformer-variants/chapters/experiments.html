Experimental logic

Change the mechanism; hold the measurement system still

Architecture comparisons become misleading when each model receives a different corpus, token budget, optimizer, or evaluation slice. I treated the recipe as the intended intervention and the rest of the pipeline as controlled infrastructure. That does not make every pair a perfect ablation—Vanilla and Modern deliberately differ in several components—but it makes those bundled changes visible and keeps accidental variation out of the result. The MoE expert width was reduced so its top-two active FFN parameters match the dense SwiGLU FFN within 0.1%.

The main configuration uses eight Transformer blocks, width 512, eight query heads, 1,024-token sequences, tied token/output embeddings, no dropout, and the GPT-2 vocabulary. Every recipe trains for 7,629 optimizer steps with an effective batch of 65,536 tokens, or exactly 499,974,144 tokens per run. Seeds 42, 137, 2,024, 31,415, and 271,828 provide independently initialized checkpoints for the primary estimates.

Dataset engineering

Preparing FineWeb-Edu for sustained model consumption

FineWeb-Edu is a filtered collection of educational web text, not a model or a tokenizer. The raw stream contains documents; the trainer needs contiguous token sequences with predictable I/O, resumable position tracking, and a stable train/ validation split. The preparation pipeline bridges that gap without loading the billion-token corpus into memory.

01

Stream and filter

Documents are read incrementally. Quality and length checks operate as records pass through, which bounds memory and makes rejection statistics observable rather than silently changing the corpus.

02

Tokenize and delimit

The GPT-2 tokenizer converts text into integer IDs; end-of-document tokens preserve document boundaries in the continuous stream. Shared tokenization prevents vocabulary differences from becoming an architectural confound.

03

Write binary shards

Token IDs are stored as compact uint16 shards with a manifest and integrity metadata. Training memory-maps the active shard instead of deserializing the whole dataset, supporting stable throughput at billion-token scale.

04

Resume exactly

The data loader persists shard identity, cursor position, and RNG state with the checkpoint. A resumed run continues from the same token boundary instead of replaying or skipping an unknown part of the training stream.

Design trade-off

Sequential memory-mapped shards simplify provenance, throughput, and exact recovery. They do not provide unrestricted example-level shuffling across the entire corpus. That choice favors repeatable large-scale consumption over the illusion of perfect global randomization.

Objective and optimization

The same language-modeling task drives every recipe

Each input sequence is shifted by one token. At position t, the model sees only the causal prefix and predicts token t + 1. The dense objective is mean next-token cross-entropy. Lower loss means the model assigns more probability to held-out targets; perplexity is the exponential of that loss, so even a modest loss difference is multiplicative in average token uncertainty.

LCE=−1T∑t=1Tlogpθ(xt+1|x≤t)

MoE recipes add two router regularizers. The load-balancing term discourages a small subset of experts from receiving nearly every token; the router z-loss controls the scale of routing logits. These terms improve routing stability, but they also mean MoE's optimized objective is not numerically identical to the dense objective. Reported validation loss remains the comparable next-token cross-entropy component.

Measurement design

One experiment, three fairness axes

Equal tokens, equal elapsed time, and equal estimated FLOPs are not interchangeable. A model with more conditional capacity may learn more from each token while spending longer on each update. A model with highly optimized dense kernels may progress farther in a wall-clock budget even if its statistical efficiency is lower. The report therefore keeps all three views.

Fixed tokens

Question: after seeing the same amount of data, which recipe predicts held-out tokens best?

Captures: statistical efficiency and usable capacity.

Misses: time, memory pressure, and implementation overhead.

Fixed wall-clock

Question: by the same elapsed training time, which implementation has progressed farthest?

Captures: actual hardware behavior, kernels, and routing overhead.

Misses: portability across devices and implementations.

Fixed estimated FLOPs

Question: for a modeled arithmetic budget, which recipe achieves lower loss?

Captures: an algorithm-oriented compute comparison.

Misses: memory traffic, occupancy, and whether nominal FLOPs execute efficiently.

Long-context protocol

Change available history, keep the scored targets fixed

Comparing perplexity over unrelated 1K and 4K passages would mix context length with target difficulty. Instead, the evaluator draws eight fixed validation windows per checkpoint and always scores the same final 256 target tokens. At 1K, 2K, and 4K, only the amount of preceding history changes. Each checkpoint first produces a mean over windows; the error bars then use the five independent checkpoint seeds as the uncertainty units.

This design separates additional history from different targets, but it remains an extrapolation test: every model trained at 1,024 tokens. It also distinguishes an unsupported model from a poor one. Vanilla's learned table cannot represent positions above 1,023, and missing cache interfaces are reported as unsupported instead of assigning a fabricated zero or silently emulating another path.

1K

Score final 256 tokens with up to 768 tokens of earlier history.

2K

Score the same target locations with a longer visible prefix.

4K

Score the same targets again; changes now reflect additional history and length extrapolation.

Fault tolerance

Recovery preserves experimental identity, not only model weights

Long GPU runs are vulnerable to process failure, storage interruption, numerical spikes, and partial checkpoint writes. A restart that restores only parameters can silently alter the optimizer trajectory or replay data, creating a run that no longer corresponds to its declared seed and token budget.

Checkpoints therefore capture the model, optimizer, scheduler, scaler state where applicable, RNG states, data-loader cursor, step, and consumed-token count. Saves use a CPU snapshot and atomic replacement so the training process never exposes a half-written checkpoint as valid. SHA-256 verification, ring rotation, and fallback recovery provide a known-good predecessor. A rolling health monitor watches loss and gradient norms, rejects non-finite updates, and keeps anomalies from polluting its own reference window.

The recovery path was tested, not merely designed

In a controlled failure demonstration, I corrupted the newest checkpoint, detected the checksum mismatch, fell back from step 2 to the verified step-1 checkpoint, and replayed the interrupted update. The resumed and uninterrupted runs ended with exactly the same loss and a maximum absolute parameter difference of 0.0. Exact recovery therefore protects the independent-seed design and consumed-token denominator; infrastructure state is part of the experimental state.
